大约一周前，我在 Sequoia Ascent 2026 大会上进行了一次炉边谈话。以下是一些要点：

我首先强调的是，LLM（逻辑逻辑模型）的意义远不止于加速现有流程（例如编码）。以下是三个新方向的例子：

1. menugen：一个可以被 LLM 完全掌控的应用程序，无需编写任何传统代码：只需输入图像，输出图像，LLM 即可原生完成操作。

2. 安装 .md 技能，而不是安装 .sh 脚本。既然可以用文字描述安装过程，然后告诉 LLM “只需把这段文字展示给你的 LLM 即可”，为什么还要编写复杂的 Software 1.0 bash 脚本来安装软件呢？ LLM 是一个高级英语解释器，能够智能地根据您的设置进行安装，并能进行所有内联调试等等。

3. LLM 知识库就是一个例子，它展现了传统代码无法实现的功能，因为它需要对来自任意来源、格式任意的非结构化数据（知识）进行计算，包括纯文本文章等等。

我之所以着重讨论这些，是因为在每一次新的范式转变中，显而易见的改进总是围绕着加速或提升现有功能展开，但这里我们却看到了一些功能示例，这些功能要么突然间可能根本不应该存在（1、2），要么在以前根本无法实现（3）。

第二个（持续进行的）主题是试图解释 LLM 中存在的锯齿状模式。一个单一的组件如何能够同时做到以下两点：1）对一个 10 万行代码库进行连贯的重构；*并且* 2）告诉你去洗车店洗车。我之前写过，这个问题源于领域的可验证性，而在这里，我进一步阐述，它也与经济学有关，因为收入/TAM（潜在市场规模）决定了前沿实验室在强化学习过程中选择将哪些内容打包到训练数据分布中。相对而言，要么你身处数据分布之中（沿着强化学习的轨道），一路顺风顺水；要么你就像拿着砍刀在丛林里越野。我对这个结论仍然不太满意，但如果你想在实际应用中利用低阶学习模型（LLM）的强大功能，同时避免其陷阱，那么构建一个准确的LLM能力模型始终是一个挑战，这也引出了……

最后一个主题是智能体原生经济。将产品和服务分解为传感器、执行器和逻辑（涵盖所有 1.0/2.0/3.0 计算范式），如何使信息对 LLM 最大程度地易读，关于快速兴起的智能体工程及其技能集、相关招聘实践等的一些说明，甚至可能暗示/设想完全神经计算在（经典）CPU 协处理器的帮助下处理绝大多数计算。

#### 中文正文

随着代理商成为软件的最大用户群体，所有软件都必须以无头模式运行。代理商将不再使用您的用户界面，而是直接与您的 API 交互。

因此，问题就变成了：未来软件的商业模式以及这种无头模式的发展方向是什么？

以下是我们基于 Box 的观察和实践，以及与其他平台的交流，对未来发展趋势的一些思考。

1) 席位不会消失。席位仍然是一种便捷高效的方式，让客户能够以可预测的方式，在一定用户基线使用范围内使用技术。关键在于，当客户付费购买席位时，席位必须包含一定数量的 API 使用额度，供代理商代表该用户使用。

用户需要能够通过与其合作的任何代理商与其数据和底层工具进行交互，而席位本身就包含一定数量的 API 使用额度。我估计大多数软件（包括 Box）都会允许用户通过 ChatGPT、Codex、Claude、Gemini、Cursor、Copilot、Perplexity、Factory、Cogniton 等系统，以相对较高的数据量无缝地处理数据。如果不这样做，那就注定失败。

2) 如果代理在系统中执行有状态的工作，它们也可以拥有“席位”，但它们的定价方式与用户截然不同。当代理拥有自己的工作空间、存储自己的数据、需要与用户不同的权限集等等时，席位（或类似概念）就显得很有意义。

如果公司希望某个代理长期运行，那么它很可能被视为系统中的另一个“用户”。Openclaw 风格的代理就展现了这种未来可能的样子。

这里唯一的定价问题是，一个客户可能决定用一个代理完成所有工作，而另一个客户可能将其拆分到 1000 个代理中。因此，像按人头计费那样定价几乎是不可能的，也不切实际；每家公司都会采取不同的方法，因为要完美地捕捉代理席位的所有价值非常棘手。

3) 对于超出席位配额或代理完全自主运行的无头使用情况，主流定价模式将是消费模式。许多企业软件平台之前都采用过这种PaaS模式，代理就像是系统中的另一个机器用户。

在某些情况下，API的定价可能与之前相同，但在其他情况下，可能需要新型API来表示代理一次性完成的工作——更像是结果——而不是一系列API调用。当无头软件本身也嵌入了代理用例时，例如通过AI协调自身系统内的流程，这一点尤为重要。

总而言之，这种使用模式的增长实际上是无限的，因为代理在这些系统中处理数据的用例将远远超过人们今天使用数据和工具的方式。所有采用无头架构的平台（也就是任何想要利用代理的平台）都需要采用类似的模型。有些人可能一开始会抵制，但这势在必行，因为平台之外的代理数量总是会远远超过用户数量。

总而言之，由于这些系统的无头架构应用，软件领域还有许多非常有趣的变革即将到来。目前还处于早期阶段。

**As agents become the biggest users of software, then all software has to be availab…**

As agents become the biggest users of software, then all software has to be available in a headless fashion. Agents won’t be using your UI, they’ll be talking to your APIs.

So the question becomes what is the business model of software and this headless approach in the future?

Here are a few thoughts on how everything plays out based on what we’re seeing and doing at Box, but also conversation with other platforms.

1) Seats don’t go away for *people*. Seats are still a convenient and efficient way to have a customer use technology predictably for a set of users within a baseline set of usage. The key, though, is that when the customer pays for a seat, it has to come with a set of usage of APIs on behalf of that user that the agent can use on their behalf. 

The user will need to be able to interact with their data and the underlying tool via any agent they work with, and an embedded amount of usage will come with the seat. I would imagine most software -Box included- will enable seats to work with their data at a relatively high volume via systems like ChatGPT, Codex, Claude, Gemini, Cursor, Copilot, Perplexity, Factory, Cogniton, et al. quite seamlessly. If you don’t do this, you’re DOA.

2) Agents may have “seats” if they are doing stateful work in the system, but they will be priced very differently than people. Seats (or the equivalent) can make sense when you have an agent that has its own workspace, stores its own data, needs a different set of permissions compared to the user, and so on. 

If a company wants this agent to be around for long period of time, that may very well look like another “user” in the system. Openclaw-style agents highlight what this future could look like. 

The only issue on pricing here is that one customer could decide to do all their work in 1 agent, and another might split it into 1,000 agents. So pricing like a human seat is nearly impossible and impractical; each company will have a different approach for this as it gets tricky perfectly trying to capture all the value within an agent seat.

3) The dominant pricing for headless use that goes above the seat allotment, or when an agent is firmly acting on their own, will be a consumption model. Many enterprises software platforms have previously operated like this with PaaS options, and agents will look like another machine user of their system. 

In some cases the APIs might get priced just as they did previously, but in other cases there may need to be new types of APIs that represent the work an agent would do in one go -more akin to an outcome- instead of a series of API calls. This is especially germane when the headless software also has an agentic use-case embedded within in, such as orchestrating the process within their own system via AI.

Overall the growth of this usage pattern is effectively unbounded as the use-cases for agents operating on data in these systems will dramatically exceed what people do with their data and tools today. Every platform that goes headless (which will be anyone that wants to take advantage of agents) will need to adopt a model like this. Some may fight it initially but it’s an inevitably as there will always be more and more agents outside your platform than people.

Overall, there’s a lot of really interesting changes left to come in software due to headless use of these systems. Early days.

#### 中文正文

没有观点本身就是一种强硬观点。

人们常常把“强硬观点”和“通用性”视为对立面，但它们并非如此。

当你决定哪些概念存在、哪些是可见的、哪些是构成要素、哪些是延伸、哪些是隐藏的——你其实已经表达了一种世界观。“没有观点”本身就是一种强有力的观点。

构建通用性意味着要表达非常具体的内容：核心概念应该少而精，持久且灵活。用户不应该被困在僵化的工作流程中。抽象比表面上的专业化更重要。系统应该能够折叠成多种形态，而不会破坏其底层逻辑。

这也是为什么纯粹以客户为中心会失败的原因。用户反馈会告诉你哪里存在摩擦，但它很少会告诉你底层系统应该是什么样子。如果你只关注用户的直接需求，你就会陷入局部最优解——功能碎片化、工具狭窄、产品围绕着当前的习惯而非持久的概念而设计。

设计就存在于这个差距之中。设计的工作是将现实简化到显而易见的层面之下。

伟大的系统并非始于产品的倍增。他们首先将概念简化到本质——直到基本要素清晰明了。然后，为每个概念构建扩展、组合和融入其他概念的路径。形式可以多种多样，但本质不应改变。

这使得系统既能服务于初学者，又不限制专家；既能服务于特定领域，又不被其束缚。

灵活性并非缺乏观点，而是源于一种高度凝聚的坚定信念——并非关乎某种理想的工作流程，而是关乎哪些概念是根本的，哪些抽象概念应该保留，哪些自由度至关重要。

核心简洁，边缘开放。这才是最终的理念。

no opinion is opinionated

people treat "opinionated" and "general purpose" as opposites. they're not.

the moment you decide what concepts exist, what's visible, what composes, what extends, what hides – you've already expressed a worldview. "no opinion" is itself a strong one.

building for universality means saying something very specific: core concepts should be few, durable, and flexible. users shouldn't be trapped in rigid workflows. abstraction matters more than surface specialization. the system should fold into many shapes without breaking its underlying logic.

this is also why pure customer-centricity falls short. user feedback tells you where friction is. it rarely tells you what the underlying system should be. if you only follow direct user demand, you converge on local maxima – fragmented features, narrow tools, products shaped around current habits rather than enduring concepts.

that gap is where design lives. the work of simplifying reality below the level that's immediately obvious.

great systems don't start by multiplying products. they start by reducing concepts to their essence – until the primitives become clear. then you build paths for each concept to extend, combine, fold into others. the packaging can vary. the essence shouldn't.

this is what lets a system serve beginners without capping experts. serve one domain without being trapped by it.

flexibility isn't the absence of opinion. it's the result of a strong opinion held in cohesion – not about one ideal workflow, but about which concepts are fundamental, which abstractions should endure, which degrees of freedom matter.

simple at the core. open at the edges. that's the ultimate opinion.
